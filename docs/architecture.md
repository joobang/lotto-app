# 데이터와 API 설계

## 저장소와 실행 구조

이 레포는 SwiftUI 앱, 로또 제품 문서, API 계약과 앱 테스트의 원본이다. 서버가 필요해지는 첫 버전에서는 기존 Render의 NestJS 프로세스에 별도 `LottoModule`을 추가하고 PostgreSQL의 `lotto` 스키마에 추첨 이력을 저장하는 방향을 사용한다. 로또는 일정 도메인·계정·수집 작업과 독립된 모듈로 둔다. 저장한 개인 조합은 초기 버전에서 기기에 보관하며, 분석 요청에서만 선택한 번호를 API로 전송한다.

## 추첨 데이터

추첨 레코드에는 회차, 한국 달력 기준 추첨일, 정렬된 본번호 6개, 보너스 번호, 출처, 확인 시점을 저장한다. 회차를 기본키로 사용한다.

초기 검토에서 공개 JSON의 1~1251회가 연속이라는 점을 확인했다. 1~1249회는 두 공개 자료에서 추첨일과 번호가 일치했고, 1251회는 공식 결과와 대조했다. 초기 운영 적재 전에 후보 스냅샷을 고정하고, 최신·경계 회차 및 출처가 불일치하는 항목을 공식 결과로 확인한다. 실제 적재 범위와 대조 범위를 기록한다. [동행복권 공식 회차별 목록](https://www.dhlottery.co.kr/lt645/winNumber) · [초기 이력 후보](https://papaya5rhw1984.github.io/lotto-data/all.json) · [비교 자료](https://busebu.com/lotto/download)

매주 추첨 이후 새 회차를 갱신한다. 회차가 연속인지, 본번호가 1~45 범위의 서로 다른 여섯 수인지, 보너스가 본번호와 다른지 검사한 뒤 반영한다. 잘못된 입력이나 중간 실패가 있으면 마지막 정상 이력으로 계속 응답한다. 같은 회차 재수집은 중복을 만들지 않는다. 값이 달라진 공식 정정은 출처와 변경 전후를 확인한 뒤 처리한다.

## 분석 실행

추첨 이력이 작으므로 첫 버전은 전체 스캔과 번호 집합 비교로 계산한다. 저장된 이력에서 마지막 정상 검증 회차를 기준으로 한 번의 응답에 일관된 집계 범위를 사용한다. 랜덤 뽑기는 기기에서, 역대 통계 뽑기는 서버에서 실행한다. 엔드포인트, 계산, 오류 처리는 [로또 API 계약](lotto-api.md)을 따른다.

## 업데이트 흐름

매주 추첨 후 공개 원천에서 새 회차를 읽고, 직전 정상 회차에 이어지는 데이터를 검증한 다음 함께 반영한다. 초기 전체 적재와 주간 추가 작업은 같은 검증 규칙을 사용한다. 정상으로 확인한 회차를 응답에 표시하며, 임시 조회 실패를 0건 통계로 해석하지 않는다. 공유 백엔드의 일정 수집과 로또 적재는 별도 작업으로 실행한다.

검사 순서와 착수 조건은 [구현 계획](implementation-plan.md)에 둔다.
